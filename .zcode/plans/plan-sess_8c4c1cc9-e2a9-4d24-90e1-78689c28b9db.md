## Plan: Fix and Align iOS Training Pipeline with win_lic Reference

The iOS port at `ios/` is architecturally sound (~4600 lines, 25 files) but the training layer has **8 compilation-blocking MLX Swift API errors** and the training logic doesn't match the `win_lic` reference. This plan fixes both.

### Phase 1: Fix MLX Swift Compilation Errors (blocking — nothing builds without this)

**File: `ios/Sources/Training/OnDeviceTrainer.swift`**

1. **`valueAndGrad` with custom struct → `[MLXArray]` API**
   - MLX Swift's `valueAndGrad` only accepts `MLXArray` / `[MLXArray]`, not custom structs.
   - Rewrite `performOptimizationStep` to pack 6 params into `[MLXArray]`, call `valueAndGrad { (arrays: [MLXArray]) -> MLXArray in ... }`, unpack gradients back into `GaussianParams`.

2. **`optimizer.apply(grad:value:learningRate:)` → manual 6-group Adam**
   - MLX Swift's `Adam` class has no per-call `apply` method; it works via `Module`/`update`.
   - Replace with a custom `ManualAdam` struct holding 6 separate (m, v) state dictionaries, each with its own constant learning rate matching win_lic:
     - position: 0.00016, feature_dc: 0.005, feature_rest: 0.00025, opacity: 0.05, scaling: 0.005, rotation: 0.001
     - betas (0.9, 0.999), eps 1e-15
   - Remove the `MLXOptimizers.Adam` import and the `TrainingLearningRates` struct (folded into ManualAdam).

3. **Fix `keepdims` → `keepDims`** (line 669, `normalizeQuaternions`)

**File: `ios/Sources/Training/MLXRasterizer.swift`**

4. **`argsort` → `argSort`** (line 122)
5. **`takeAlongAxes(array, indices, axis:)` → `takeAlong(array, indices, axis:)`** (line 448)
6. **Free function `asType(inFront, .float32)` → method `inFront.asType(.float32)`** (line 112)
7. **`.broadcast([h,w])` → `broadcast(array, to: [h,w])`** throughout (lines 244-245, 250-251, 270-272, 280, 297-298)
8. **Fix in-place indexed assignment in `paddedImage`** — `result[...] = image` returns a new MLXArray that must be captured. Rewrite using `where`/`at` or construct the padded array functionally.

### Phase 2: Align Training Logic with win_lic

**File: `ios/Sources/Training/MLXRasterizer.swift`**

9. **Add depth rendering to the rasterizer**
   - The alpha-blend loop currently accumulates only RGB color. Add a parallel accumulation of depth (alpha-weighted z values) so we get a rendered depth map `[H, W, 1]` alongside the RGB `[H, W, 3]`.
   - Return both from `render()`: `(rgb: MLXArray, depth: MLXArray)`.

10. **Add depth L1 loss with masking**
    - `Ll1_depth = |rendered_depth[mask] - gt_depth[mask]|.mean()` where `mask = (gt_depth > 0) & (rendered_depth > 0)`.
    - Weighted by `lambda_depth = 0.005`.
    - Combined loss: `(1 - λ_dssim) * L1 + λ_dssim * (1 - SSIM) + λ_depth * L1_depth`

**File: `ios/Sources/Training/OnDeviceTrainer.swift`**

11. **Replace naive 5% clone densification with win_lic extend pattern**
    - Remove the current `densify()` that clones existing Gaussians with position perturbation.
    - Implement `extend()`: when processing a new keyframe, render current model to get alpha map, find LiDAR points where `rendered_alpha < 0.99` (map not yet opaque), create new Gaussians there with depth-based scale init, append to params.
    - No clone/split/prune, no gradient threshold — matching win_lic's append-only approach.

12. **Load depth maps as training targets**
    - Currently `loadTargetImages` only loads RGB. Add parallel loading of depth maps (Float32 `.bin` files) as MLX arrays for the depth supervision loss.

13. **Fix learning rates to win_lic constants** (no scheduler)
    - Already partially correct in `TrainingLearningRates.default`, but now embedded in the ManualAdam struct. Ensure `scaling_scale = 1.0` (not the current 0.01 — win_lic uses `scaling_scale_` from config, default 1.0).

### Phase 3: Fix Runtime Bugs

**File: `ios/Sources/UI/CaptureView.swift`**

14. **Fix dual ARSession bug**
    - `ARCameraPreview` creates its own `ARView` with its own `ARSession.run(config)`.
    - `CaptureSession.startPreview()` creates a separate `ARKitSensorSource` with its own `ARSession`.
    - Two competing ARKit sessions on a real device → camera conflicts.
    - Fix: Share a single ARSession. Have `ARCameraPreview` use `CaptureSession.sensorSource.session` if available, or have `CaptureSession` own a single `ARView` whose session is shared with the sensor source.

**File: `ios/Sources/Capture/FrameRecorder.swift`**

15. **Fix IMU write inefficiency**
    - `writeIMU()` opens and closes a `FileHandle` per sample (100 Hz × 2 file ops per sample).
    - Fix: Keep a persistent `FileHandle` for `imu.csv` (like trajectory.txt), close it in `stop()`.

### Phase 4: Documentation & Cleanup

**File: `ios/README.md`**

16. **Update README** — currently says iOS 27+, msplat, RealityKit GaussianSplatComponent. Update to reflect: iOS 18+, MetalSplatter for rendering, MLX Swift for training, correct source structure (no PLYLoader.swift, add MLXRasterizer.swift).

**File: `ios/Package.swift`**

17. **Remove unused `MLXRandom` import** if not needed after densification rewrite (may still be needed for initial shuffling).

### What This Plan Does NOT Change
- **Sensor layer** (ARKitSensorSource, IMURecorder, SensorFrame) — already correct and well-designed
- **Rendering layer** (SplatRealityView, SplatSceneManager) — MetalSplatter integration is solid
- **Models** (DeviceProfile, GaussianSplat, TrainingRecord) — fine as-is
- **Utilities** (FileStorage, MetalHelpers, DepthVisualization) — fine as-is
- **DatasetExporter / OffDeviceTrainingBridge** — fine as-is
- **SH degree**: Stays at SH0 (3 DC coefficients) for on-device training. PLY export writes 45 zero-filled f_rest values, which is standard format-compatible. Full SH3 on-device training would be too memory-intensive for iPhone.
